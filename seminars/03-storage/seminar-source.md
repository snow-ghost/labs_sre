## Подготовка и порядок работы

Это полный текст проведения по слайдам 34-49 презентации ЛК5. Продолжительность принята равной 80 минутам, как у лекционной пары. Время в расписании отсчитывается от начала семинара, поскольку время начала этой пары не указано. Речь, вопросы и ответы приведены непосредственно в разделах слайдов. Пометки в квадратных скобках обозначают работу студентов и не читаются вслух. Команды выполняются поэтапно, после соответствующего объяснения.

До занятия нужна отдельная учебная виртуальная машина Linux, Bash, не менее 4 ГиБ оперативной памяти и 12 ГиБ свободного места на ее учебной файловой системе. Размеры выбраны для файла fio на 2 ГиБ, образа LVM на 4 ГиБ и запаса. Пакеты: fio, sysstat, lvm2, thin-provisioning-tools, util-linux, kmod, Python 3 и sudo; названия могут различаться между дистрибутивами. Для части LVM нужны поддержка петлевых устройств, тонких пулов и снимков ядром, а также утилита thin_check. В контейнере эти возможности могут быть недоступны даже для root. Установка пакетов, подготовка виртуальной машины и проверка доступа выполняются до пары. Предупреждение об отсутствии thin_check нельзя пропускать: проверка метаданных в таком случае может быть отключена.

На учебной виртуальной машине до занятия проверяются необходимые команды и модули. Успех этих команд еще не заменяет пробное создание и удаление стенда.

```bash
sm3_check_tools() {
  local tool
  for tool in fio iostat pidstat lvm thin_check losetup python3; do
    command -v "$tool" || return 1
  done
  sudo modprobe loop || return 1
  sudo modprobe dm_thin_pool || return 1
  sudo modprobe dm_snapshot || return 1
}
sm3_check_tools
```

Запускается именно fio для тестирования ввода-вывода. Команда `fio --version` должна сообщить версию вида `fio-3.x`; одноименная программа из другого пакета не подходит. Команда `fio --enghelp=io_uring` проверяет наличие движка в сборке, но не возможность его запуска при действующих ограничениях ядра. После подготовки файла нужен короткий пробный запуск. Если io_uring не работает, согласованная замена для всех запусков сравнения глубины: libaio с direct=1. При отсутствии обоих движков используется учебная таблица слайда 41.

Перед занятием на учебной машине в основном терминале Bash создается новый рабочий каталог. Все дальнейшие блоки этого документа рассчитаны на тот же терминал и его переменные. Второй терминал служит только для наблюдения. После закрытия основного терминала восстановление переменных и соответствия устройств выполняется по сохраненному состоянию с преподавателем; повторять создание наугад нельзя.

```bash
sm3_prepare_directory() {
  SM3_ROOT=$(mktemp -d "$(pwd -P)/sm3.XXXXXX") || return 1
  cd "$SM3_ROOT" || return 1
  mkdir fio-lab || return 1
  pwd
  findmnt -T ./fio-lab || return 1
  df -hT ./fio-lab || return 1
  lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
}
sm3_prepare_directory
```

Каталог создается на заранее выбранной учебной файловой системе. Новый каталог предотвращает совпадение имен с прежним опытом, но не изолирует нагрузку от других пользователей общего хранилища. На общем рабочем сервере этот практикум не запускается.

После проверки пути и свободного места заранее готовится полностью записанный файл. Здесь происходит реальная запись 2 ГиБ, поэтому этот блок относится только к выделенной учебной машине. При любой ошибке подготовка прекращается. Команды сгруппированы в функции: return останавливает текущий этап, сохраняя терминал и переменные для диагностики. К следующему этапу переходят только после успешного завершения предыдущего.

```bash
sm3_prepare_file() {
  test "$PWD" = "${SM3_ROOT:?}" || return 1
  test ! -e ./fio-lab/test.bin || return 1
  test ! -L ./fio-lab/test.bin || return 1
  fio --name=prepare --filename=./fio-lab/test.bin \
    --size=2G --rw=write --bs=1M --ioengine=psync \
    --direct=1 --end_fsync=1 --group_reporting=1 \
    --output-format=json --output=./fio-lab/prepare.json || return 1
  stat -c '%n %s bytes' ./fio-lab/test.bin
}
sm3_prepare_file
```

Ожидаемый размер: 2147483648 байт. Файл, полученный только через truncate, для измерения чтения не подходит: разреженные области могут читаться без обращения к физическим данным. Подготовка не входит в 80 минут. Если direct=1 не поддерживается файловой системой, причина выясняется до занятия; режим не меняется незаметно для группы.

Следующий блок определяет помощник sm3_fio. Он добавляет общие параметры чтения и записывает результат в отдельный каталог серии. Перед каждым запуском сохраняются начало, конец и код завершения; эти отметки используются для выбора интервала iostat. Время в самом JSON fio не принимается за гарантированную отметку начала. Существующий результат никогда не перезаписывается. После ошибки или при повторении сравнения команда sm3_new_results создает новый каталог; затем соответствующая серия выполняется заново целиком.

```bash
sm3_new_results() {
  local next_results
  next_results=$(mktemp -d "${SM3_ROOT:?}/fio-lab/results.XXXXXX") \
    || return 1
  SM3_RESULTS=$next_results
  printf '%s\n' "$SM3_RESULTS"
}
sm3_fio() {
  local name="${1:?}" status out
  shift
  [[ "$name" =~ ^[a-zA-Z0-9-]+$ ]] || return 1
  out="${SM3_RESULTS:?}/$name.json"
  if test -e "$out" || test -L "$out" \
    || test -e "$SM3_RESULTS/$name.time" \
    || test -L "$SM3_RESULTS/$name.time"; then
    printf 'Результат уже существует: %s\n' "$out"
    return 1
  fi
  date -Is > "$SM3_RESULTS/$name.time" || return 1
  if fio --readonly --allow_file_create=0 --name="$name" \
    --filename="${SM3_ROOT:?}/fio-lab/test.bin" --size=2G \
    --numjobs=1 --time_based=1 --group_reporting=1 \
    --output-format=json --output="$out" "$@"; then
    status=0
  else
    status=$?
  fi
  date -Is >> "$SM3_RESULTS/$name.time" || return 1
  printf 'exit=%s\n' "$status" >> "$SM3_RESULTS/$name.time" || return 1
  return "$status"
}
sm3_new_results
sm3_fio probe --rw=randread --bs=4k --direct=1 \
  --ioengine=io_uring --iodepth=4 --runtime=3
```

Пробный запуск должен завершиться с кодом 0. Проверяются JSON, отсутствие ошибок и ненулевое число чтений. При выборе libaio эта замена вносится и в пробный запуск, и в серию слайда 40. Проба не входит в таблицу результатов сравнения. Доступный процессор и лимиты ресурсов фиксируются: генератор нагрузки тоже может стать ограничением.

Доступны два варианта участия. На подготовленной машине студент выполняет измерения fio и работает с LVM. Без подходящего окружения студент решает вопросы по учебным данным слайдов 39, 41, 43, 44 и 46, составляет таблицу, диагноз и план следующей проверки. В отчете указывается выбранный вариант. Учебные числа нельзя выдавать за результаты запуска.

Команды сверены с руководствами инструментов и проверены в изолированной виртуальной машине с Linux 6.8, fio 3.36 и LVM 2.03.16. Выполнены все семь измерений fio и проверено извлечение их результатов; отдельный прогон подтвердил создание пула, тома, снимка и последующую очистку. Автоматическое расширение через службу наблюдения в этой проверке не запускалось. Совместимость с выбранным учебным образом преподаватель проверяет до занятия.

## Слайд 36. Правила безопасности
<!-- duration: 4 -->

Сейчас проверьте, что работаете в своей учебной виртуальной машине и находитесь в созданном для семинара каталоге. Файл test.bin уже подготовлен. На этапах измерения мы будем только читать этот файл. В командах включена защита от профиля записи и запрещено создание отсутствующего файла.

Эти ограничения полезны, но они не проверяют происхождение среды за нас. Каталог с названием fio-lab на рабочем сервере все равно относится к рабочему серверу. Если неясно, кому принадлежит хранилище, используем учебную таблицу.

Мы не будем доводить тонкий пул до заполнения. Такой опыт может привести к ошибкам или зависанию записи и требует отдельного плана восстановления. Ситуацию с заполнением метаданных разберем по условию задачи.

При ошибке команды остановитесь на этом шаге и сохраните сообщение. Не добавляйте принудительные ключи и не повторяйте весь блок целиком. Частично созданная конфигурация уже имеет состояние, которое нужно сначала увидеть.

## Слайд 37. Шаг 1. Зафиксировать окружение

Начнем с наблюдений, которые ничего не перенастраивают. Записываем время, версии, файловую систему и цепочку устройств. findmnt показывает файловую систему для конкретного пути, а lsblk помогает понять связи между блочными устройствами.

Дата связывает измерение с журналом событий. Версии нужны потому, что поля и возможности инструментов меняются. Свободная память помогает интерпретировать повторное чтение файла: наш рабочий набор имеет размер 2 ГиБ, а доступное место для кеша может быть меньше или больше него.

Найдите устройство, на котором лежит тестовый каталог. Если видите логический том, проследите его до нижнего устройства. Строки логического и физического уровней могут учитывать одну и ту же работу на разных этапах. Складывать их как независимую нагрузку нельзя.

## Слайд 38. Шаг 2. Снять iostat без теста
<!-- duration: 5 -->

До запуска fio посмотрим фон. В системе уже могут работать журналирование, обновления, резервное копирование и другие процессы. Их операции попадут в статистику устройства вместе с нашим тестом.

<!-- slide-code -->
```bash
LC_ALL=C S_TIME_FORMAT=ISO iostat -xz -y -t -k 1 10

# Во втором терминале:
pidstat -d 1 10

# Сообщения ядра:
journalctl -k --since "-10 min" | tail -n 80
```

Ключ -x включает расширенные показатели. -y исключает первый отчет с момента загрузки, а -t добавляет отметки времени. Интервал равен одной секунде, после десяти отчетов команда завершится. -z скрывает устройства без активности, поэтому отсутствие строки не всегда означает отсутствие устройства.

pidstat помогает увидеть процессы с дисковой активностью. Но он не описывает все внутренние операции ядра и не видит процессы на сервере удаленного хранилища. Отсутствие подходящего процесса в его выводе не исключает внешнюю конкуренцию.

Запишите, есть ли операции чтения и записи до нашего опыта. Посмотрите, стабилен ли фон. Если на той же виртуальной машине идет большое обновление, сравнение одного режима до обновления и другого во время него будет нечестным.

Пустой вывод журнала при отсутствии прав также не доказывает отсутствия ошибок. В отчете нужно различать "проверили, сообщений нет" и "доступ к журналу недоступен".

[Работа студентов: 2 минуты. Сохранение исходного состояния и короткое описание фоновой активности.]

Во время дальнейших запусков собираем iostat непрерывно во втором терминале. Десяти секунд недостаточно для покрытия теста на сорок пять секунд. В основном терминале выведите путь командой `printf '%s\n' "$SM3_RESULTS"`. Во втором терминале выполните следующий блок и вставьте этот путь в ответ на запрос:

```bash
read -r -p 'Абсолютный путь SM3_RESULTS: ' SM3_RESULTS
if test -d "$SM3_RESULTS"; then
  (set -o pipefail
   LC_ALL=C S_TIME_FORMAT=ISO iostat -x -y -t -k 1 \
     | tee -a "$SM3_RESULTS/iostat-session.txt")
else
  printf '%s\n' 'Каталог результатов не найден.'
fi
```

После завершения всех опытов fio остановим наблюдение сочетанием Ctrl+C. Ключ -k фиксирует вывод объема в КиБ/с; для сопоставления с МиБ/с делим на 1024. При сравнении используем только полные отсчеты внутри измеряемого интервала. После создания нового SM3_RESULTS наблюдение запускается для нового каталога. Отсчеты на границах запуска и во время прогрева исключаются; секундная статистика не дает точного разбиения внутри секунды.

## Слайд 39. Шаг 3. Буферизованный и прямой ввод-вывод
<!-- duration: 9 -->

Сначала дважды прочитаем один и тот же файл через страничный кеш. Затем прочитаем его с direct=1. Для первого и второго буферизованного запуска используются разные имена результатов. Так мы сохраним оба наблюдения.

<!-- slide-code -->
```bash
sm3_compare_cache() {
  local pass
  for pass in 1 2; do
    sm3_fio "bufread-$pass" --rw=read --bs=1M --direct=0 \
      --ioengine=psync --iodepth=1 --runtime=45 || return 1
  done
  sm3_fio dirread --rw=read --bs=1M --direct=1 \
    --ioengine=psync --iodepth=1 --runtime=45
}
sm3_compare_cache
```

Помощник sm3_fio определен в разделе подготовки. readonly запрещает задания записи. allow_file_create=0 превращает отсутствие файла в ошибку, а не в скрытый этап подготовки. При ошибке любого буферизованного запуска функция прекращает всю серию и не переходит к прямому чтению. Для всех трех запусков выбран один синхронный движок и глубина один; состав чтения и размер блока одинаковы.

Первый буферизованный запуск не называется холодным. Файл мог оказаться в кеше до опыта, а внутри сорока пяти секунд fio может прочитать его несколько раз. Повторный запуск исследует ту же систему после предыдущего чтения, но не гарантирует идеального состояния кеша.

Если во втором запуске fio показывает большой объем чтения, а статистика устройства меняется мало, это согласуется с обслуживанием из памяти. Если такой разницы нет, возможны небольшой доступный кеш, вытеснение или другой путь хранения. Мы записываем наблюдение, а не исправляем его до ожидаемой картинки.

Прямой ввод-вывод обычно обходит страничный кеш, но ниже остаются кеши гипервизора, контроллера или удаленного массива. Поэтому результат direct=1 тоже не равен универсальной физической скорости накопителя.

[Выполнение трех запусков, проверка ошибок и заполнение таблицы: 5 минут.]

В каталоге SM3_RESULTS рядом с каждым JSON лежит файл .time с началом, концом и кодом завершения команды. По нему и журналу iostat найдите соответствующий интервал, исключая создание файла и соседние запуски. Все три JSON-файла сохраняются для отчета.

Какая ошибка возникнет, если скорость повторного чтения из памяти назвать скоростью диска? Мы припишем устройству работу, которую оно могло почти не выполнять. Эту проверку полезно делать всякий раз, когда число выглядит неожиданно большим.

Для работы без виртуальной машины используйте следующие учебные значения. Они предполагают сопоставимый небольшой фон, один подготовленный файл и совпадающие интервалы. Это условные числа для интерпретации, не измерения оборудования.

| Режим чтения | fio, МиБ/с | Чтение устройства, МиБ/с |
|---|---|---|
| Буферизованный, первый запуск | 600 | 48 |
| Буферизованный, повторный запуск | 900 | 2 |
| Прямой | 160 | 163 |

Во второй строке рост работы fio сочетается с малой активностью устройства, что согласуется с кешированием. Небольшое превышение объема устройства над fio в третьей строке может включать фоновую работу и различия учета. Эти данные не доказывают, какой именно физический кеш участвовал в удаленной или виртуальной среде.

## Слайд 40. Шаг 4. Изменить iodepth
<!-- duration: 8 -->

Теперь меняем профиль целиком: случайное чтение блоками 4 КиБ, прямой ввод-вывод и асинхронный движок. Результаты этого этапа сравниваем между собой. С предыдущим последовательным чтением блоками 1 МиБ нельзя сравнивать их как изменение одной только глубины.

Внутри нового профиля меняется только iodepth. Одно задание последовательно пройдет значения один, четыре, шестнадцать и шестьдесят четыре. Каждый результат получит отдельное имя.

<!-- slide-code -->
```bash
sm3_compare_depth() {
  local depth
  for depth in 1 4 16 64; do
    sm3_fio "rr-q$depth" --rw=randread --bs=4k --direct=1 \
      --ioengine=io_uring --iodepth="$depth" --ramp_time=5 \
      --runtime=30 || return 1
  done
}
sm3_compare_depth
```

Пять секунд прогрева не входят в итоговую статистику fio. Для iostat при анализе исключаем этот участок отдельно. Отметка начала команды предшествует инициализации движка, поэтому точное начало измерения по ней не определяется: для учебного сравнения берем центральный устойчивый участок и указываем его границы. Заданная глубина означает желаемый параллелизм. В отчете fio проверяем распределение фактически достигнутой глубины. При синхронном движке или ограничении среды увеличение одного параметра не гарантирует увеличения одновременно выполняемых операций.

Если io_uring недоступен, весь набор выполняется заново с согласованным libaio. Смешивать два результата одного движка с двумя другого как чистый опыт над глубиной нельзя.

[Четыре запуска, проверка JSON и заполнение таблицы: 4 минуты.]

Файл JSON можно открыть текстовым редактором. Для чтения fio обычно важен раздел jobs, затем read. В современных версиях задержка завершения находится в clat_ns; p99 в percentile с ключом 99.000000. Значение в наносекундах делим на миллион для получения миллисекунд. bw_bytes делим на 1048576, чтобы получить МиБ/с. Пример извлечения приведен в приложении к документу.

Проверьте, что поле error равно нулю и измерение действительно выполнило чтение. Запуск с ошибкой исключается из сравнения производительности. По одному проходу можно сформулировать предварительную гипотезу; устойчивость небольших различий проверяется повторными запусками.

## Слайд 42. Шаг 6. Собрать безопасный LVM стенд
<!-- duration: 8 -->

Переходим от скорости к управлению емкостью. Новый стенд будет размещен в отдельном файле образа. Он покажет физический том PV, группу VG, тонкий пул и виртуальный том LV. Для измерения характеристик реального накопителя такая вложенная схема не подходит.

Основной терминал остается в нашем рабочем каталоге. Копируем подготовленный блок из документа, а затем выполняем функцию со слайда. Функции проверки можно определить заранее; вызовы создания выполняются на этом этапе. При каждом расхождении останавливаемся.

```bash
sm3_check_loop() {
  local details backing
  [[ ${SM3_LOOP:-} =~ ^/dev/loop[0-9]+$ ]] || return 1
  [[ ${SM3_VG:-} =~ ^vg_sm3_[0-9]+_[0-9]+$ ]] || return 1
  test "${SM3_IMAGE:-}" = "${SM3_ROOT:?}/fio-lab/lvm.img" || return 1
  test -f "${SM3_IMAGE:-}" || return 1
  test ! -L "$SM3_IMAGE" || return 1
  test -b "$SM3_LOOP" || return 1
  details=$(sudo losetup --list --json --output BACK-FILE \
    "$SM3_LOOP") || return 1
  backing=$(printf '%s\n' "$details" | python3 -c \
    'import json,sys; print(json.load(sys.stdin)["loopdevices"][0]["back-file"])') \
    || return 1
  test "$backing" = "$SM3_IMAGE" || return 1
  test "$(sudo losetup --list --noheadings --raw \
    --output OFFSET "$SM3_LOOP")" = 0 || return 1
  test "$(sudo blockdev --getsize64 "$SM3_LOOP")" = 4294967296
}
sm3_prepare_lvm() {
  test "$PWD" = "${SM3_ROOT:?}" || return 1
  test ! -e "$SM3_ROOT/fio-lab/lvm.img" || return 1
  test ! -L "$SM3_ROOT/fio-lab/lvm.img" || return 1
  SM3_IMAGE="$SM3_ROOT/fio-lab/lvm.img"
  SM3_VG="vg_sm3_$(date +%s)_$$"
  sudo vgs -o vg_name >/dev/null || return 1
  if sudo vgs "$SM3_VG" >/dev/null 2>&1; then
    printf '%s\n' 'Такая группа уже существует. Остановка.'
    return 1
  fi
  truncate -s 4G "$SM3_IMAGE" || return 1
  SM3_LOOP=$(sudo losetup --find --show --nooverlap "$SM3_IMAGE") \
    || return 1
  printf '%s\n' "$SM3_IMAGE" "$SM3_LOOP" "$SM3_VG" \
    > ./fio-lab/lvm-state.txt || return 1
  sm3_check_loop || return 1
  sudo losetup --list "$SM3_LOOP" || return 1
  lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS "$SM3_LOOP"
}
sm3_prepare_lvm
```

Файл состояния нужен для проверки и восстановления контекста; исполнять его как сценарий не нужно. В имени группы используются время и номер процесса, чтобы отделить опыт от других групп. Проверяем, что петлевое устройство относится именно к нашему файлу, имеет размер 4 ГиБ, нулевое смещение и не смонтировано. JSON используется для точного чтения пути, в том числе с пробелами. Только после этого переходим к созданию LVM. Если сохранение файла состояния завершилось ошибкой, устройство уже может быть подключено: зафиксируйте выведенные значения переменных и проверьте losetup, прежде чем повторять какие-либо действия.

<!-- slide-code -->
```bash
# Подготовка и проверка SM3_LOOP описаны в документе.
sm3_create_lvm() {
  sm3_check_loop || return 1
  sudo pvcreate "$SM3_LOOP" || return 1
  sudo vgcreate "$SM3_VG" "$SM3_LOOP" || return 1
  sudo lvcreate --type thin-pool -n pool -L 3G \
    "$SM3_VG" || return 1
  sudo lvcreate --type thin -n app -V 8G \
    --thinpool pool "$SM3_VG" || return 1
  sudo lvs -a -o+devices "$SM3_VG"
}
sm3_create_lvm
```

PV включает петлевое устройство в управление LVM. VG объединяет его пространство. Пул получает область данных размером 3 ГиБ и отдельные служебные области. Том app получает виртуальный размер 8 ГиБ. Физического пространства на восемь гигабайт здесь не появилось.

[Создание и проверка стенда студентами: 4 минуты. При отсутствии прав используется описание этой конфигурации.]

Проверьте, что app связан с pool именно в нашей группе. Файловую систему на app в этом обязательном опыте не создаем и запись на том не запускаем. Так далее мы наблюдаем структуру и учет пула, а изменение блоков разбираем по отдельному учебному примеру.

## Слайд 43. Шаг 7. Контролировать тонкий пул
<!-- duration: 6 -->

Посмотрим, чем виртуальный размер отличается от реального расхода. В выводе lvs находим именно строку пула. Data% показывает заполнение его области данных, Meta% заполнение метаданных. Показатель Data% отдельного тонкого тома относится к этому тому, поэтому читать разные строки как одинаковую величину нельзя.

<!-- slide-code -->
```bash
sudo lvs -a -o \
  lv_name,lv_size,pool_lv,data_percent,metadata_percent,seg_monitor \
  "$SM3_VG"
sudo lvs -a -o+chunksize,devices "$SM3_VG"
sudo vgs -o vg_name,vg_size,vg_free "$SM3_VG"
systemctl status lvm2-monitor --no-pager
sudo lvmconfig --type full activation/thin_pool_autoextend_threshold
sudo lvmconfig --type full activation/thin_pool_autoextend_percent
```

У пустого app расход данных может быть близким к нулю, хотя виртуальный размер уже равен 8 ГиБ. Метаданные могут занимать ненулевое место с момента создания. Конкретное значение зависит от версии и параметров; одинаковый процент для всех машин не требуется.

seg_monitor помогает проверить участие в наблюдении, но одной этой колонки недостаточно для обещания авторасширения. Нужны работающий механизм, действующая политика и свободное место группы. В системе без systemd команда systemctl неприменима; это ограничение среды, а не доказательство отсутствия всех механизмов LVM.

Какой порог выбрать? Начнем со времени на реакцию. Допустим, пул данных равен 3 ГиБ, занято 60 процентов, а расход растет на 12 МиБ в минуту. Свободно около 1229 МиБ, то есть примерно сто две минуты при неизменной скорости. Если реакция и расширение занимают сорок минут, такой расчет дает запас, который еще нужно проверить на всплески. Метаданные считаем отдельно.

[Проверка показателей и расчет своего порога: 2 минуты.]

Штатная политика тонкого пула может реагировать на заполнение данных и метаданных. Нельзя автоматически считать ее настроенной только на данные. Проверяем фактическую конфигурацию и возможность выделения места для обеих областей. Значение порога 100 в соответствующем параметре LVM отключает авторасширение.

## Слайд 44. Шаг 8. Снимок и согласованность
<!-- duration: 6 -->

Создадим тонкий снимок app. Исходный том пуст и не смонтирован, поэтому в этом опыте нет незавершенных операций приложения. Снимок понадобится сохранить до этапа удаления, чтобы порядок очистки был одинаковым для всей группы.

<!-- slide-code -->
```bash
sm3_snapshot() {
  sm3_check_loop || return 1
  test "$(sudo pvs --noheadings -o vg_name "$SM3_LOOP" \
    | tr -d '[:space:]')" = "$SM3_VG" || return 1
  sudo lvcreate --snapshot -n app_snap "$SM3_VG/app" || return 1
  sudo lvs -a -o \
    lv_name,origin,pool_lv,data_percent,metadata_percent "$SM3_VG"
}
sm3_snapshot
```

В выводе должна появиться строка app_snap с происхождением от app и связью с тем же пулом. Создание снимка не означает копирования восьми гигабайт данных. В нашем пустом стенде нет большого набора записанных блоков, поэтому выраженный рост Data% ожидать незачем.

[Создание снимка и поиск трех строк: app, app_snap и pool. 1 минута.]

Чтобы объяснить дальнейшие изменения, используем условную модель уже заполненного тома. Это не вывод команд нашего стенда. В пуле 3 ГиБ лежат 384 МиБ данных: заполнение области данных около 12,5 процента. Снимок сначала разделяет эти блоки с исходным томом. Если после снимка исходный том изменит 128 МиБ общих данных и сохранит старую версию для снимка, занятый объем в упрощенной модели вырастет до 512 МиБ, примерно 16,7 процента. Реальное распределение учитывает размер порций и метаданные.

После удаления единственного снимка старые блоки, которые больше никому не нужны, могут освободиться. Это объясняет, почему длительное хранение снимков влияет на расход места. В нашем обязательном опыте такая запись не выполняется; вывод о росте здесь получен из модели.

Теперь вопрос о работающей базе: означает ли снимок одного блочного тома, что все ее транзакции согласованно сохранены?

[Ответы студентов: 30 секунд.]

Нет. Для согласованной копии нужны правила самого приложения, а иногда общая точка для нескольких томов. Блочный снимок обычно рассматривается как состояние для восстановления после аварийного завершения. Наличие нужных журналов и поддерживаемой процедуры определяет, сможет ли база восстановиться. Независимая резервная копия дополнительно должна переживать выбранный отказ исходного пула.

## Слайд 45. Шаг 9. Удалить учебный LVM стенд
<!-- duration: 5 -->

Очистка начинается с повторной проверки владельца объектов. Если основной терминал закрывался, переменные пропали или устройство отличается от сохраненного, останавливаемся и восстанавливаем соответствие по lvm-state.txt, losetup и pvs. Нельзя выбирать свободное на вид устройство по его номеру.

В нашем обязательном сценарии на логическом томе нет файловой системы и точки монтирования. Если вы самостоятельно добавляли их, сначала нужно прекратить использование и размонтировать их; стандартный порядок ниже к такой измененной конфигурации без проверки не применяется.

Перед удалением выполняем дополнительную проверку: группа должна содержать ровно один физический том, и это наш проверенный петлевой файл. Если найдены дополнительные логические тома, выясняем их происхождение до очистки.

```bash
sm3_check_vg() {
  local names
  sm3_check_loop || return 1
  test "$(sudo pvs --noheadings -o vg_name "$SM3_LOOP" \
    | tr -d '[:space:]')" = "${SM3_VG:?}" || return 1
  test "$(sudo pvs --noheadings -o pv_name \
    --select "vg_name=$SM3_VG" | tr -d '[:space:]')" = "$SM3_LOOP" \
    || return 1
  names=$(sudo lvs --noheadings -o lv_name "$SM3_VG") || return 1
  names=$(printf '%s\n' "$names" | awk '{$1=$1;print}' | LC_ALL=C sort)
  test "$names" = $'app\napp_snap\npool'
}
sm3_verify_detached() {
  local attempt attached
  for attempt in 1 2 3 4 5; do
    attached=$(sudo losetup -j "${SM3_IMAGE:?}") || return 1
    test -z "$attached" && return 0
    sleep 1
  done
  printf '%s\n' 'Образ еще подключен; сохраните его и проверьте потребителей.'
  return 1
}
sm3_check_vg
sudo lvs -a -o lv_name,vg_name,pool_lv,devices "$SM3_VG"
```

На слайде операции завершаются при ошибке. Подтверждение удаления относится только к названным учебным объектам. Принудительные ключи не нужны.

<!-- slide-code -->
```bash
sm3_cleanup() {
  local lv
  sm3_check_vg || return 1
  for lv in app_snap app pool; do
    sudo lvremove "$SM3_VG/$lv" || return 1
  done
  sudo vgremove "$SM3_VG" || return 1
  sm3_check_loop || return 1
  sudo pvremove "$SM3_LOOP" || return 1
  sudo losetup -d "$SM3_LOOP" || return 1
  sm3_verify_detached
}
sm3_cleanup
```

## Приложения

### Восстановление контекста после закрытия терминала

Этот блок только читает сохраненное состояние и проверяет связь образа с устройством. Введите абсолютный путь своего рабочего каталога. Перед продолжением снова определите функции sm3_check_loop, sm3_check_vg и sm3_verify_detached из документа, не вызывая функции создания. Файл состояния нельзя исполнять через source: он содержит данные, а не команды.

```bash
sm3_restore_state() {
  local saved
  local -a state
  read -r -p 'Рабочий каталог SM3_ROOT: ' saved || return 1
  test -d "$saved/fio-lab" || return 1
  SM3_ROOT=$(cd "$saved" && pwd -P) || return 1
  mapfile -t state < "$SM3_ROOT/fio-lab/lvm-state.txt" || return 1
  test "${#state[@]}" -eq 3 || return 1
  SM3_IMAGE=${state[0]}
  SM3_LOOP=${state[1]}
  SM3_VG=${state[2]}
  test "$SM3_IMAGE" = "$SM3_ROOT/fio-lab/lvm.img" || return 1
  [[ "$SM3_LOOP" =~ ^/dev/loop[0-9]+$ ]] || return 1
  [[ "$SM3_VG" =~ ^vg_sm3_[0-9]+_[0-9]+$ ]] || return 1
  cd "$SM3_ROOT" || return 1
  sudo losetup -j "$SM3_IMAGE" || return 1
  printf 'Образ: %s\nУстройство: %s\nГруппа: %s\n' \
    "$SM3_IMAGE" "$SM3_LOOP" "$SM3_VG"
}
sm3_restore_state
```

После восстановления переменных выполняется sm3_check_loop. Если проверка не прошла, изменения запрещены: старый номер петлевого устройства мог получить другой образ. Пустой успешный вывод losetup -j означает, что образ уже отсоединен. Ошибка чтения состояния имеет другой смысл и не считается подтверждением очистки.

При прерванном удалении нельзя повторять создание. С преподавателем определяется последний успешно завершенный шаг по выводу lvs, vgs, pvs и losetup. Полная sm3_cleanup намеренно требует наличия ровно app, app_snap и pool; при частичном удалении она откажется работать. После повторной проверки принадлежности оставшиеся команды удаления выполняются по одной. Это отличается от обхода защиты: для каждого оставшегося объекта заново подтверждается его связь с учебным образом. Неизвестные дополнительные тома не удаляются.

### Извлечение показателей из JSON fio

Блок выполняется в основном терминале после трех запусков сравнения кеширования и четырех запусков случайного чтения. Каталог одной серии передается через SM3_RESULTS. Блок ничего не записывает и рассчитан на формат fio с clat_ns и bw_bytes. Проверяется ровно одно задание в каждом файле. Отсутствие файла или поля означает незавершенную серию либо другой формат; такой результат не заменяется нулем.

```bash
python3 - "${SM3_RESULTS:?}" <<'PY'
import json
import sys
from pathlib import Path

folder = Path(sys.argv[1])
print('Запуск | IOPS | МиБ/с | p50, мс | p95, мс | p99, мс')
names = ['bufread-1', 'bufread-2', 'dirread']
names += [f'rr-q{depth}' for depth in (1, 4, 16, 64)]
for name in names:
    path = folder / f'{name}.json'
    report = json.loads(path.read_text())
    if len(report['jobs']) != 1:
        raise SystemExit(f'{path}: требуется одно задание')
    job = report['jobs'][0]
    if job['error'] != 0:
        raise SystemExit(f'{path}: ошибка fio {job["error"]}')
    result = job['read']
    if result['total_ios'] == 0:
        raise SystemExit(f'{path}: нет операций чтения')
    percentiles = result['clat_ns']['percentile']
    delays = [percentiles[k] / 1_000_000
              for k in ('50.000000', '95.000000', '99.000000')]
    print(name, round(result['iops'], 1),
          round(result['bw_bytes'] / 1048576, 2),
          *(round(value, 3) for value in delays), sep=' | ')
    print('Распределение глубины:', job['iodepth_level'])
PY
```

Для серии повторов сохраняются отдельные каталоги. Процентили разных запусков не усредняются как обычные измерения задержки: среднее нескольких p99 не является p99 объединенного набора операций. В учебном отчете достаточно показать p99 каждого запуска и разброс IOPS. Итоговый процентиль для объединенной выборки требует исходных данных или подходящих гистограмм.
